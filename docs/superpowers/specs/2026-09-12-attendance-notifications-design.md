# Attendance notifications — design (sub-project #2b)

Date: 2026-09-12 · Branch: `claude/attendance-notifications` (off `origin/release/play-store` @ `862e61cd`,
v2.17.1+60) · Release: MINOR **2.18.0+61** (new capability), user approval before merge/push.

## 1. Why

Employees only find out they missed a check-in or check-out when HR asks, or when they open the app.
#2b tells them in time to act, and tells System Managers when the attendance terminal or its sync
agent goes quiet. It builds on:

- the two-shift model released in 2.17.0+59 / 2.17.1+60 (`resolveShifts`, `deriveShiftStatus`,
  `ShiftDayStatus`, Shift Assignments, per-shift Attendance rows);
- the documents-digest notification infrastructure released in 2.11.0+50 / 2.14.0+55 (WorkManager
  one-off chain, background isolate on the persisted session cookie, `flutter_local_notifications`);
- the live `Attendance Sync Status` heartbeat (sub-project #0).

## 2. Decisions (user, 2026-09-12)

| Topic | Decision |
|---|---|
| Audience | Every user linked to a tracked Employee; **on by default**, with an off switch |
| Platform | **Android only** (iOS can't check punches at fire time; iOS builds are cut separately) |
| Missed check-in | **Both**: a heads-up 10 min before each shift's cut-off, and a reminder at the cut-off |
| Check-out | About **10 min after each shift ends**, if checked in but not out |
| Recap | ~07:30 on working days, **only when the day had a problem** |
| Terminal alert | System Managers; watched **every 30 min 06:00–22:00** on working days; alert on change (quiet / back) |
| Approach | **A — checks on the phone** (Android background task); no server changes, no Firebase |

## 3. Facts this design rests on (verified 2026-09-12)

| Shift Type | Start–end | Check-in window | Check-out window closes | Late cut-off |
|---|---|---|---|---|
| Morning | 08:00–12:15 | from 06:00 | 13:00 | 08:15 |
| Afternoon | 13:30–20:00 | from 13:00 | 22:00 | 13:45 |
| Morning (Fri) | 08:00–12:00 | from 06:00 | 13:15 | 08:15 |
| Afternoon (Fri) | 14:30–20:00 | from 13:15 | 22:00 | 14:45 |

- Shifts come from Shift Assignments generated by HRMS (on 12 Sep: 16/16 tracked employees had a
  Morning and an Afternoon assignment). `Employee.default_shift` is empty; `General` is retired.
- HRMS writes one Attendance row per shift after its check-out window closes; Leave Application rows
  carry `shift` = ''.
- Employee role reads its own Employee Checkin, Attendance, Shift Assignment and Shift Type; not Holiday
  List (the app uses `hrms.api.get_attendance_calendar_events`, weekly offs included). Employee, HR User,
  HR Manager and System Manager can read the Single DocType `Attendance Sync Status`
  (`terminal_online`, `terminal_last_seen`, `terminal_alias`, `agent_last_run`, `last_upload`; naive
  Asia/Dubai times).
- Heartbeat consumer rule (spec #0 §5): **syncing** ⇔ `now − agent_last_run ≤ 20 min` AND
  `terminal_online` AND `now − terminal_last_seen ≤ 20 min`; anything else (or an unreadable document) is
  **unknown**.
- Digest infra facts: WorkManager allows **one** background dispatcher per app
  (`Workmanager().initialize(digestCallbackDispatcher)` in `main.dart`); the digest uses unique work
  `digest-notification` / task `digestTask`; the background isolate authenticates with the persisted
  `PersistCookieJar` in `<appSupportDir>/.cookies/`; the instance URL is mirrored into GetStorage; the
  isolate must **never write** the main GetStorage box (cross-isolate last-writer-wins). No notification
  tap routing exists. The Notifications settings entry is gated by `showNotificationsEntry()` (manager
  only) in `user_area_screen.dart`.
- `attendance_logic.dart` and `attendance_models.dart` import only `intl` and each other, so they run in
  the background isolate as they are. `User` carries `employeeId` and `roles`.

To verify during implementation (not blocking the design): the Employee role can read its own approved
Leave Application; if not, the leave check relies on the Attendance row alone.

## 4. Parts and data flow

1. **Shared dispatcher.** The one WorkManager dispatcher routes by task name: `digestTask` →
   `runDigestTask` (unchanged), `attendanceTask` → `runAttendanceTask`. Separate unique work names
   (`digest-notification`, `attendance-notification`), so neither chain cancels the other.
2. **`attendance_timeline.dart`** (pure). Input: the employee's shifts for the day (or none), whether the
   day is a working day, whether the user is a System Manager, `now`. Output: the day's moments
   (kind, shift, time) and the next wake time after `now`:
   - heads-up: cut-off − 10 min, per shift;
   - missed check-in: cut-off, per shift;
   - check-out: shift end + 10 min, per shift;
   - recap: 07:30 on working days;
   - terminal watch (System Managers): every 30 min from 06:00 to 22:00 on working days.
   After the last moment of the day — or on a day with no moments (holiday, no schedule, reminders
   off) — the next wake is a **planning run at 05:55 the next day**, which fetches that day's data and
   schedules its first moment, so the chain never stops.
3. **`attendance_notify_service.dart`** (isolate-safe, like `DigestService`, single `callGet` seam).
   Session probe `frappe.auth.get_logged_user` first (Guest/401/403 ⇒ auth expired). Reads, as the user:
   own Employee (`attendance_device_id`), own Shift Assignments for the day, the Shift Types they name,
   own Employee Checkins for the day, own Attendance for the day and the recap window, own approved
   Leave Applications covering the day, the holiday calendar, and `Attendance Sync Status`.
4. **`attendance_notify_rules.dart`** (pure). Decides, for one moment and the fetched data, whether to
   notify and the exact text (§5). Reuses `resolveShifts`, `deriveShiftStatus` and a pure
   `isSyncing(status, now)` for the heartbeat rule.
5. **`attendance_notify_worker.dart`** (`runAttendanceTask`). Reads the user and preferences from the main
   box read-only; returns early when logged out, not linked, or both features are off. Fetches, then
   evaluates **every moment of today whose time ≤ now that has not been posted yet and is still useful**
   (§5.1 rule 5) — so a late or planning run catches up without repeating. Posts, and writes its own
   state to a **separate GetStorage container `attendance_notify`** written only by the worker: the
   posted-moment keys for today (`<date>|<shift>|<kind>`, pruned daily), the last recapped day, the
   terminal state + since, and the last auth-expired notice date. Re-arms in a `finally` so one failure
   never ends the chain.
6. **`AttendanceNotifyScheduler`** has two entry points. `rearm()` (main isolate: app start, login /
   session re-check, settings changes) registers a **planning run in 1 minute** — the main isolate doesn't
   know today's shifts — or cancels the work when the user is logged out, not linked / not a System
   Manager, or both features are off. `scheduleNext(wake)` (worker) registers the next wake computed from
   the fetched timeline. Both use one-off work `attendance-notification` (`ExistingWorkPolicy.replace`,
   `NetworkType.connected`). `cancelAttendanceOnLogout()` cancels the work and clears posted attendance
   notifications.

Tapping any attendance notification opens the app (Dashboard, where My attendance shows the details).

## 5. Rules and wording

### 5.1 Employee reminders (heads-up, missed check-in, check-out)

A reminder for a shift is posted only when **all** hold:

1. the user is linked to an Employee with an `attendance_device_id`, and attendance reminders are on;
2. the shift comes from the employee's own Shift Assignment covering the day, or from an Attendance row
   naming it — never from the `General` / `ShiftRules.fallback` fallback;
3. the day is not a holiday on their calendar, no approved Leave Application covers it (a half-day leave
   also silences the whole day — the app can't tell which half), and their Attendance for it is not
   `On Leave`;
4. the heartbeat says **syncing** (unknown ⇒ held back: nobody is told they didn't punch when the
   terminal is at fault);
5. delivery is still useful: a heads-up only before its cut-off; a missed check-in only before the
   shift ends; a check-out only before the check-out window closes.

| Kind | Also requires | Title | Body |
|---|---|---|---|
| Heads-up | no punch for that shift yet | Check in for the Morning shift | Punch before 08:15 to be on time. |
| Missed check-in | still no punch for that shift | No check-in for the Morning shift | Nothing recorded since 08:00. Punch now; this shift will show late. |
| Check-out | an IN for that shift, no OUT after it | Check out of the Morning shift | In at 07:58, no check-out yet. Punch before 13:00. |

Shift names use `ShiftRules.shortName` ("Morning (Fri)" → "Morning"); times are the shift's own
(cut-off, start, window end). Punches are split between shifts exactly as the Attendance screen does
(`deriveShiftStatus` per shift). Each shift's reminders share one notification id, so the missed
check-in replaces the heads-up; when a later run finds the person has punched, a stale heads-up /
missed check-in for that shift is cancelled. Copy never blames the person ("No check-in recorded",
never "you forgot").

### 5.2 Recap

At the 07:30 moment on a working day: take the most recent day in the last 3 days that is after the last
recapped day and has the user's own Attendance rows. If any row is Absent, Late (`late_entry`), Early
exit (`early_exit`) or No check-out (Present/Late with no `out_time`), post:
**Yesterday's attendance** (or **Attendance on Thu 10 Sep** when it isn't yesterday) —
"Morning: late 12 min · Afternoon: no check-out." Either way, record that day as recapped. On Leave,
Holiday, Half Day and Work From Home are never problems.

### 5.3 Terminal watch (System Managers)

At each watch moment, evaluate `isSyncing`. Compare with the stored state:

- syncing → quiet: **Attendance terminal quiet** — "No sync since 09:12. Check-ins may not be arriving;
  staff reminders are paused." (`since` = the older of `agent_last_run` / `terminal_last_seen`);
- quiet → syncing: **Attendance terminal back** — "Syncing again since 09:47.";
- no change: nothing. The first run of a session with no stored state alerts only if quiet.

The heartbeat being unreadable counts as quiet. A System Manager who is also a tracked employee gets
both sets of notifications.

## 6. Settings, permission, channels

- **Entry:** `showNotificationsEntry()` also shows the Notifications row for any Android user linked to a
  tracked Employee (managers keep it as today).
- **Attendance reminders** section (linked employees): switch, default **on** — stored as
  `notif_att_enabled::<user>`, absent ⇒ on. **Terminal alerts** switch for System Managers, default on
  (`notif_att_terminal::<user>`). The documents digest section stays manager-only and unchanged.
- **Permission (Android 13+):** the Dashboard requests notification permission once for a linked employee
  with reminders on (flag `notif_att_prompted::<user>` in the main box, written by the main isolate). If
  denied, the settings section shows a line explaining how to allow notifications; no repeated prompts.
- **Channels:** `attendance_reminders` "Attendance reminders" (Importance.high, short vibration) for
  employee reminders and the recap; `attendance_terminal` "Attendance terminal" (Importance.high) for
  System Manager alerts. No alarm style.
- **Notification ids** (a block distinct from the digest's `1001` and the iOS reminder block 2000–2055):
  `3000 + shift index` (0 = the day's first shift, 1 = the second) for per-shift reminders, `3010`
  recap, `3020` terminal, `3030` session expired.

## 7. Failures

- **Session expired:** at most once per day, "Open Multimax to keep attendance reminders working" on the
  reminders channel (date kept in the `attendance_notify` box). Otherwise reminders would stop silently.
- **Any other fetch/notify failure:** nothing is posted; the worker still re-arms (`finally`); the next
  moment is the retry. The dispatcher always returns `true` (no WorkManager backoff).
- **Offline at the due time:** WorkManager runs the task when the network returns; rule 5.1.5 drops
  reminders that are no longer useful.
- **Doze / battery saver:** timing is approximate; accepted (Approach A).

## 8. Testing

- Unit (pure): timeline — Saturday, Friday, holiday, no assignment, System Manager watch, next wake
  across midnight, 05:55 planning run on a day with no moments; catch-up — a run at 10:00 posts the
  Morning missed check-in once and a second run posts nothing (posted-moment keys); rules — every gate in
  5.1, each wording, late delivery, stale-reminder cancel, recap
  selection within the 3-day window and the "not yesterday" title, terminal state changes incl. first run
  and unreadable heartbeat; `isSyncing` at the 20-min boundaries.
- Service: fake `callGet` — session expired, 403 on a single read, happy path.
- Scheduler: fake `WorkScheduler` — registers `attendance-notification` at the next wake; cancels when
  logged out / not linked / both features off; digest chain untouched.
- Dispatcher routes `digestTask` and `attendanceTask`.
- Widget: Notifications entry visibility (manager / linked employee / neither); settings sections per
  role; permission-denied hint.
- On device (Android): a reminder at a shift cut-off with and without the terminal syncing; check-out
  reminder; recap next morning; System Manager quiet/back alerts; battery-saver timing.
- `flutter analyze` then the full suite, sequentially.
